# Словарь предметной области

Термины, которые встречаются в коде и остальных доках. Если ты не из мира VPN/прокси —
начни отсюда.

## Ядра (cores)

Внешние нативные бинарники, которые реально гоняют трафик. Приложение их запускает и
кормит JSON-конфигом.

| Ядро | Что делает | Где |
|------|------------|-----|
| **keqrnel** | единый бинарь: sing-box-хост со встроенным xray-движком. **Дефолтное ядро** (`coreEngine: keqrnel`) — один процесс вместо связки, меньше RAM. | Windows/Linux |
| **xray** | прокси-движок: протоколы (VLESS/VMess/Trojan/SS/Hysteria2), локальный SOCKS/HTTP, маршрутизация по доменам/IP/geoip. Целевая версия — **26.x**. | все платформы (на Windows — внутри keqrnel; отдельный `xray.exe` в бандл не входит) |
| **sing-box** | владеет TUN-устройством на десктопе: забирает системный трафик и отдаёт аплинку (SOCKS от xray). Используется в режиме `chain`. | Windows/Linux TUN |
| **wireproxy** (`wireproxy-awg`) | реализует AmneziaWG и отдаёт его локальным SOCKS/HTTP (proxy-режим без админ-прав). | Windows/Linux |
| **tun2socks** | на Android превращает TUN-трафик в SOCKS-запросы к xray. | Android (внутри VpnService) |
| **geoip.dat / geosite.dat** | базы для правил `geoip:` / `geosite:` (страны IP / категории доменов). | рядом с ядром |

## Режимы и пути трафика

- **Proxy-режим** — локальный SOCKS/HTTP (например, `127.0.0.1:2080`); на Windows
  дополнительно прописывается системный прокси, чтобы браузеры пошли через него. Без
  админ-прав, но не весь софт уважает системный прокси.
- **TUN-режим** — виртуальный сетевой адаптер, **весь** трафик ОС в туннеле. Админ-права
  (Windows) / root через `pkexec` (Linux). На Android аналог — `VpnService`, и там режим
  всегда TUN.
- **`ConnectionMode`** — `proxy` | `tun`.
- **`VpnBackend`** — `xray` | `awg` (AmneziaWG идёт мимо xray-пайплайна).
- **`coreEngine`** — `keqrnel` (дефолт, один процесс) | `chain` (два процесса:
  xray → sing-box; на Windows требует докинуть бинарники — их нет в поставке).

## Протоколы

Способы «обёртки» трафика, чтобы он проходил фильтрацию.

| Протокол | Ссылка | Заметки |
|----------|--------|---------|
| **VLESS** | `vless://` | лёгкий, часто с XTLS/Reality |
| **VMess** | `vmess://` | конфиг — base64(JSON) внутри ссылки |
| **Trojan** | `trojan://` | маскируется под обычный HTTPS |
| **Shadowsocks** | `ss://` | классика; SIP002 base64 |
| **Hysteria 2** | `hysteria2://`, `hy2://` | QUIC/UDP; ссылки `hysteria://` тоже принимаются и трактуются как v2, сам протокол Hysteria v1 не поддерживается |
| **AmneziaWG** | файл `.conf` | обфусцированный WireGuard (1.0/1.5/2.0); добавляется файлом/текстом, не ссылкой |

- **Reality / XTLS** — TLS-маскировка для VLESS (поля `pbk`/`sid`/`spx`, fingerprint).
- **ALPN, SNI, fingerprint (fp), ECH** — параметры TLS-рукопожатия, влияют на незаметность.

## Подписки и серверы

- **Подписка** — URL, по которому провайдер отдаёт список серверов (обычно base64 со
  ссылками). Приложение периодически их обновляет.
- **UA-гейтинг** — многие панели маршрутизируют ответ по `User-Agent`: известным
  VPN-клиентам отдают payload, браузерам — HTML-страницу подписки (или вовсе ошибку).
  Приложение представляется как `keqdroid/<версия>`, при отказе перебирает известные
  клиентские UA и запоминает сработавший в подписке (`Subscription.userAgent`).
- **Сервер (`ServerItem`)** — одна конфигурация подключения: raw-ссылка + метаданные
  (пинг, страна, избранное). Из подписки или добавлен вручную.
- **`X-Subscription-Userinfo`** — HTTP-заголовок ответа подписки с лимитами трафика и
  датой истечения (upload/download/total/expire); показывается в UI.
- **HWID** — идентификатор устройства, который некоторые панели требуют для привязки
  подписки. Шлётся заголовками или query-параметром; включается в настройках.
- **Стабильный ключ (`_stableKey`)** — «тот же сервер» между обновлениями подписки:
  схема + uuid/пароль + host + port. Устойчив к ротации reality-параметров, чтобы при
  обновлении не терялись пинги и избранное.

## Маршрутизация (routing)

Куда пустить конкретный трафик: напрямую, через туннель или в блок.

- **direct** — мимо туннеля (локальные адреса, отечественные сайты).
- **proxy** — через сервер.
- **block** — заблокировать (реклама, телеметрия).
- **Списки правил** — смешанные: домены (`example.com`, `domain:`, `full:`, `regexp:`,
  `geosite:`), IP/CIDR (`1.2.3.4/24`), `geoip:<код страны>`.
- В **xray** geoip задаётся внутри поля `ip` (`ip: ["geoip:ru"]`) — отдельного поля
  `geoip` нет, с ним правило молча теряет силу и ядро падает с
  «this rule has no effective fields».
- **Пресеты** (`routing_presets.dart`) — готовые списки direct/proxy/block.

## Split tunneling

Какие приложения/программы пускать в туннель, а какие мимо.

- **Android** — по пакетам приложений (`includePackages`/`excludePackages`).
- **Windows/Linux** — по именам процессов, и только в TUN-режиме (в Proxy per-process
  сделать нельзя — предупреждение пишется в лог).
- **`AppRoutingMode`**: `allProxy` (всё в прокси) | `onlySelected` (только выбранные) |
  `allExceptSelected` (всё, кроме выбранных).

## Прочее

- **Kill switch** — при падении туннеля не выпускать трафик напрямую: правила
  `0.0.0.0/1` + `128.0.0.0/1` перекрывают default route и гонят всё в `proxy`.
- **LAN Proxy** — отдать локальный прокси в локальную сеть другим устройствам.
- **Пинг**: TCP (открыть соединение), ICMP (классический ping), URL (HTTP-запрос через
  прокси — реальная задержка до сайта), speed (скачать фиксированный payload → kbps).
- **Системный прокси (Windows)** — настройка ОС, которую уважают Chromium-браузеры.
  Firefox её игнорирует — для него есть `firefox_proxy_helper` (правит `user.js`).
- **MethodChannel / EventChannel** — мост Flutter↔натив; канал приложения —
  `keqdis_vpn_channel` (методы — команды нативу, события — поток статуса/статистики).
- **WorkManager** — фоновые задачи Android; обновляет подписки, даже когда приложение
  убито (минимальный интервал системы — 15 минут).
- **wintun.dll** — драйвер TUN-адаптера для Windows.
- **pkexec / polkit** — запрос root в Linux (для TUN).
- **DoH** — DNS-запросы при активном туннеле идут DNS-over-HTTPS через туннель, чтобы
  блокировка 53-го порта на VPN-сервере не ломала резолвинг.
